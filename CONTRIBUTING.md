# Правила командной работы

## Основная ветка
- `main` — основная стабильная ветка проекта.
- Не выполнять учебные задачи непосредственно в `main`.

## Ветки
Для каждой задачи создаётся отдельная ветка:
- `feature/краткое-название` — новая функциональность или материал;
- `docs/краткое-название` — документация и отчёты;
- `fix/краткое-название` — исправление ошибок.

Пример: `docs/add-individual-reports`.

## Коммиты
Коммиты должны отражать конкретное изменение. Рекомендуемый формат:
- `Добавлено: описание`
- `Исправлено: описание`
- `Обновлено: описание`

Не объединять несвязанные изменения в один коммит.

## Pull Request и проверка
1. Участник получает актуальную `main`.
2. Создаёт собственную ветку.
3. Вносит изменения и фиксирует их коммитами.
4. Отправляет ветку на GitHub.
5. Создаёт Pull Request с описанием изменений.
6. Другой участник проверяет изменения.
7. После проверки изменения объединяются с `main`.

## Документация и диаграммы
- Markdown в `docs/README.md` используется как основной текст общего отчёта.
- `docs/report.docx` поддерживается в соответствии с согласованной Markdown-версией.
- При изменении UML-диаграммы обновляются и изображение в `docs/img/`, и редактируемый исходник в `docs/draw/`.
- Не добавлять в отчёты вымышленные результаты тестирования или программной реализации.

## Локальная идентификация коммитов
Каждый участник настраивает собственные имя и email Git:
`git config user.name "Имя Фамилия"`
`git config user.email "адрес-почты"`

Настройка локального имени и email сама по себе не выдаёт доступ к GitHub: для отправки изменений нужен доступ к репозиторию.
